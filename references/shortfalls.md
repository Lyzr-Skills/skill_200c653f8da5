# First-question shortfall path: avoid scan/timeout cascades

## Decide what the question measures
For 'material shortfalls', locate `Shortfall (U)` in the candidate `IEO200 - Inventory EO by DC` module, confirm units/sign/dimensions. For 'forecast inventory below zero or below safety stock', locate closing forecast inventory and safety-stock line items instead. Never relabel unmet demand as negative inventory. If neither required measure is readable, stop.

## Exact bounded sequence
1. Reuse bound model/schema if available; otherwise bind the named model, find the candidate module by exact/filtered name, and look up only the relevant line items (plus actual inventory and safety stock only when asked or required for the full inventory-risk report). Resolve the model week from model time anchors once. Default Florida DC if user says Florida, Scenario 1 unless specified otherwise. For 'next 26 weeks', identify the 26 actual calendar members; if calendar/anchor cannot be resolved, ask instead of assuming FY labels match dates.
2. **Preferred first read:** If the module time range is limited enough to read interactively, use one paged `read_cells` call with site + Scenario 1 sliced, material and time as at most two leaf breakdown axes, and only the requested measure. This reads the model time range (not automatically just the requested 26 weeks); discard out-of-horizon weeks **only after** reading complete coverage. Do not use SQL `IN` across weeks or an unsliced aggregate as a shortcut: SQL module queries require item-sliced dimensions, and `LIMIT` restricts returned rows, not server-side source scans. If the range is too wide, look for an already-existing saved exception view/export instead of blindly requesting material × all-time. `sql_schema` is for discovering actual axes when needed, not for bypassing the item-slicing rules. If a one-week slice is requested, `read_cells` with week, site and scenario sliced and material as the sole leaf axis is the fast path. Read only the required measure, not every line item.
3. If the bounded request returns a page with `has_more`, paginate while it remains reliably responsive; record pages and coverage. A `LIMIT` restricts output rows, NOT the source cells scanned or server calculation. If any broad read times out, **do not retry the same shape and do not execute 26 weekly queries**. One narrower probe (one material or one week; one leaf axis) may establish whether the model is readable, but cannot support a full-horizon claim. If even that fails, stop and explain.
4. If a complete bounded read is not technically possible or the data is too large to complete interactively, explain that the full 26-week report needs a pre-aggregated exception view or a saved read-only export (site, scenario, week, material, shortfall/ending stock, safety stock) from the model. Do not claim that a ZIP/skill-only change cures server-side scans. Offer either a clearly labelled smaller slice or that model-side view; do not silently shrink scope.

## Report
If complete, list all observed negative-stock/safety breaches (or explicitly labelled unmet-demand shortfalls) in covered periods, first/worst week and units, with site, scenario, horizon and actual read date. If incomplete, provide only verified observations and exactly which site/weeks/materials are covered. 'Significant' has no threshold unless supplied: show largest verified gaps, not an invented threshold. Never report a count for periods not read, and do not turn forecast shortfall into a purchase-order quantity.
